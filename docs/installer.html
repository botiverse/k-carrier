Installer contract

What an installer built on K does for every way a request can arrive, every machine it can land on, and every way it can end. K's transaction is code and is fixed. This contract wraps it, and is advisory.

Still settling. K ships the transaction, bootstrapStable, the lock and the receipts; the rest of this page is the installer's. The first implementation is raft-computer-installer.

The problem

A request comes from the shell, from the application, or from a remote authority. Someone is there to answer a question, or nobody is. The machine has nothing installed, or an installation K manages, or one mid-upgrade, or one that predates K, or one that cannot start. Only the shell can reach a machine whose application is down, and only a person can consent to a repair, because a repair cannot be rolled back. Most installers answer the common cells of that space and improvise the rest, and the improvised cells are where machines get stuck.

Who can do what, where

Every entry hands the installer the same request: an id, an exact version and recorded consent. A channel is resolved to a version by the entry, and who approved it is recorded. A request selects nothing else. The same id sent twice replays the first receipt and touches nothing. Whether a person is present is decided once, before anything else: an explicit CI or *_NON_INTERACTIVE=1 wins, otherwise a tty.

How the installer reads the machine

It settles any unfinished K work before it looks, so a machine mid-upgrade is never mistaken for anything else. Then, in order: a readable stable slot means managed; a service installed before K is adopted by seeding stable from it; unresolved recovery, a corrupt slot or a dead lock owner means broken; otherwise fresh. Only managed and upgrading have rollback.

What each outcome prints

One line and one exit code. Success is claimed after the live probe, never on acceptance. Attended runs explain and may ask; unattended runs return the code and reason and let the caller decide.

Repair

The one forceful thing the installer does, and the one K never does.

  • Its own request, id and consent for this machine. A failed upgrade never escalates to it; a request that only names a version cannot reach it; it never runs unattended.
  • Recovery first, and never while a K lock owner is alive.
  • Quarantine K's state by one atomic rename; delete nothing; never touch data outside the slots. Stop an unresponsive service only by an identity you recorded, never a bare pid.
  • Install and probe exactly as an upgrade would, then bootstrapStable, so the next upgrade is a normal transaction. No rollback; the receipt says repaired, names the quarantine, the version and the approver.

What repair must keep so K's state stays sound is the normative repair boundary. Whether to offer it is a product choice.
