Installer contract

What an installer built on K should do in every situation: install, upgrade, repair, attended or not, on any machine it may find. K's transaction is code and is fixed. This page is a contract around it, and it is advisory.

This contract is still being worked out. It is not part of K's code; K ships the transaction and the primitives the contract needs. The first implementation lands in raft-computer-installer, the reference installer. Expect the wording here to change as that work settles.

The problem

A request comes from one of three places: a person at the shell, the application itself, or a remote authority. It arrives with someone present to answer a question, or unattended. And it lands on a machine in one of five worlds: nothing installed, an installation K manages, one still mid-upgrade, one installed before K existed, or one that cannot start.

Two facts couple these. The application and a remote authority can reach only a machine where the application runs; a machine that cannot start is reachable from the shell alone. And an upgrade can be rolled back, but a repair cannot, so a repair needs consent from someone who can see the result. The same request therefore means different things on different machines, and a request with nobody present must already carry its exact version and its consent.

Most installers answer the common combinations and improvise the rest. The improvised ones are where machines get stuck: a retry that installs over a half-finished upgrade, a remote push that repairs without anyone consenting, a success printed before the new process was ever probed.

One model for the whole space

Every entry launches the same external installer and hands it the same request: an id, an exact version and recorded consent. Every combination of entry, world and presence gets one behavior, one printed line and one exit code. Success is claimed only after a live probe, never when the request was accepted. Whether a person is present is decided once: an explicit CI or *_NON_INTERACTIVE=1 variable wins; otherwise a tty decides.

Five worlds, not three

A caller sees three machines: empty, running, or not starting. The installer distinguishes five, because two of them look like one of those three from outside. An unfinished operation in the journal is finished first, whatever was asked; that recovery is mandatory and is not repair. An installation that predates K is adopted, not reinstalled. K's transaction covers the managed and upgrading worlds, the only two with rollback; the installer decides the other three.

What the entry owes for each outcome

K returns an outcome, an exit code and a receipt. The entry that launched it owes these in return. Interactive means a person at the shell who can be asked and can see the result; non-interactive means a remote request or a script, where nothing may prompt and nothing may be assumed.

Repair

In the broken world K refuses rather than guesses. The installer, which runs when the application cannot, may then repair on explicit consent: run recovery first, quarantine K's state directory by one atomic rename, reinstall verified bytes, start, probe, and bootstrapStable the result so the next upgrade is a normal transaction. Give repair its own request shape, so a request that only names a version cannot reach it. Stop an unresponsive service only by an identity you recorded, never by a bare pid. A repair has no rollback and is reported as a repair, with what it displaced, what it installed and who approved it.

What such a repair must keep so that K's state stays sound is the normative repair boundary. Whether to offer repair at all is a product choice.
