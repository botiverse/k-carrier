Installer contract

What an installer built on K does for every way a request can arrive, every machine it can land on, and every way it can end. K's transaction is code and is fixed. This contract wraps it, and is advisory.

Still settling. K ships the transaction, bootstrapStable, the lock and the receipts; the rest is the installer's. The reference implementation is raft-computer-installer. Two shipped installers, Codex's and the current Raft one, are what this page was checked against; see prior art.

The problem

A request comes from the shell, from the application, or from a remote authority. Someone is there to answer a question, or nobody is. The machine has nothing installed, or an installation K manages, or one mid-upgrade, or one that predates K, or one that cannot start. Only the shell can reach a machine whose application is down, and a repair, unlike an upgrade, cannot be rolled back. Most installers answer the common cells of that space and improvise the rest, and the improvised cells are where machines get stuck.

Who can do what, where

One run, whatever the entry

The interface

What a person or a script sees. Names are the reference implementation's; the shape is the contract.

curl -fsSL https://example.com/install.sh | sh                                # attended: resolve, show, ask
curl -fsSL https://example.com/install.sh | sh -s -- --channel alpha          # attended, another channel
CI=1 curl -fsSL https://example.com/install.sh | sh                           # unattended: the channel's current release, no questions
curl -fsSL https://example.com/install.sh | sh -s -- --version 2.3.0 --yes    # this version, no questions
curl -fsSL https://example.com/install.sh | sh -s -- repair --version 2.3.0 --yes   # only a broken machine accepts this

Every run prints one line on stdout and exits 0, 1, 2 or 3. What was settled first, if anything, goes to stderr. Details go to the receipt file, not the terminal.

The rules

Request

  1. Every entry hands the installer the same request: an id, an exact version and recorded consent. It selects nothing else: no code, no commands, no URLs.
  2. A channel is resolved to one version before anything changes, and the receipt records that version, never the channel. Attended, the person sees the version and answers; unattended, the channel's current release is the target and the invocation is the consent.
  3. The same id with the same target replays the first receipt and touches nothing. A different target for the same id is refused. A new attempt is a new id.

Presence

  1. Whether a person is present is decided once, before anything else: an explicit CI or *_NON_INTERACTIVE=1 wins; otherwise a tty on stdin or /dev/tty.
  2. An entry may collect consent attended and then run the installer unattended. self upgrade does exactly this: it asks in the application, then launches the same bootstrap non-interactively with the version and the consent in the request.
  3. Unattended, nothing prompts. Running the installer is the consent to whatever the machine needs, repair included, and the receipt records who ran it and what was done; --yes only matters attended, where it skips the question. Optional side effects, such as removing another manager's copy or adding to PATH, default to no.

Lock and settle

  1. One installer per state directory, under K's lock. Another live owner is held, exit 2. Liveness is decided by the lock protocol, never by age.
  2. Every run finishes unfinished K work first, whatever was asked, and reports what it settled alongside its own outcome. This is recovery, not repair; it needs no network and no consent. Recovery that cannot settle is unresolved, exit 3, and no new work is admitted until it is.

Worlds

  1. After settling, the installer reads the machine once: a readable stable slot is managed; a service installed before K is adopted by seeding stable from its running executable; unresolved recovery, a corrupt slot or a dead lock owner is broken; nothing is fresh.
  2. Managed and adopted are K's transaction, with rollback. Fresh is verify, seed stable, publish, self-check, then first setup: no transaction, no rollback, nothing to restore. Broken is repaired the same way, and the run says so.
  3. First setup is whatever the product needs before it can run: logging in, for instance. It is the product's step and the installer only runs it. Attended, it runs on the terminal and a successful setup is followed by start and a live readback. Unattended, there is nobody to set it up, so the installation is left usable and the line says what to do next. A declined or failed setup leaves a usable installation, not a failed one.
  4. An installation owned by another manager, such as a package manager, is held, exit 2. The installer may say where it is and, attended, offer to remove it. It never removes it unattended.
  5. A target older than what is installed is held, exit 2, unless the request says the downgrade is intended. Refusing to downgrade is not success.

What the product reports

Worlds describe the installation. Two more things describe the product, and only the product can answer them. The installer asks after reading the world and before stopping anything.

  1. Is a service running? Read before anything is stopped, and remembered for recovery. A running service is stopped and must come back as a live service. A service that was not running is not started by an upgrade; the candidate is run for its version instead. The user's choice to have it stopped is kept.
  2. Is the product set up? Logged in, configured, licensed: whatever it needs before it can run. Not set up and attended, a fresh install runs first setup and then starts. Not set up and unattended, nothing is started and the line names the next step. An upgrade never runs first setup; it repeats the next step if the product still names one.
  3. Neither answer changes what is verified: bytes, platform, self-reported version, then a process of the new bytes. They change only which process answers, and what the line says.

Verify

  1. The release authority and the byte store are different trust domains. When both describe the target, their sha256 and size must agree before any download.
  2. Bytes are verified against the manifest, after decompression if compressed, and again after staging. The staged executable must match the host platform and must report the requested version when asked. Any mismatch fails before any change, exit 1.
  3. Downloads fail before anything changes; recovery needs none. Credentials for a private source come from the environment unattended, and may be prompted for attended.

Repair

  1. Repair is what a broken machine gets, and only a broken machine: a failed upgrade never escalates to it, and on a machine that can be upgraded a repair request is held. Attended, it is asked about once like any other action, naming what will be quarantined. Unattended, running the installer is the consent, as for everything else.
  2. Settle first. Never under a live lock. Quarantine K's state by one atomic rename; delete nothing; never touch data outside the slots. Stop an unresponsive service only by an identity you recorded, never a bare pid.
  3. Install and probe exactly as an upgrade would, then bootstrapStable, so the next upgrade is a normal transaction. No rollback; the receipt says repaired, never promoted, and names the quarantine, the version and the approver. What repair must keep is the normative repair boundary.

Report

  1. Success is read back from a process of the new bytes, never inferred. An accepted request, a finished download, a replaced file: none of these is success.
  2. What the readback reaches depends on what was running. A service that was running is stopped and must come back as a live service reporting the requested version, a pid and a new start id. Where nothing runs, because nobody has set the product up yet, the candidate itself is run and must answer as the requested version; every run is a new process, so the start id is new. The line says which: Upgraded 2.2.1 → 2.3.0. It is running. against Upgraded 2.2.1 → 2.3.0. Next: run app login.
  3. Installed means usable, not running: the bytes are in place and answer as the version. Running is claimed only when the service was started and read back, after first setup or because it was running before. The product names the next step when there is one, and the line repeats it.
  4. Every run ends in one printed line and one exit code: 0 upgraded, installed or up to date, 1 failed or rolled back, 2 not done, 3 unresolved. The line says what happened, what did not change, and what to do next, in the user's words.
  5. Attended, the line explains and may point at a next command. Unattended, it is the same line plus the code, and the caller decides; the installer never retries the same target on its own.

The line is in the user's words. Slots, journals, receipts, operation ids and quarantines are how the installer works, not what it says; they live in the receipt file. A path is fine when the user may need it, such as where an old installation was kept or which file retries a recovery.
