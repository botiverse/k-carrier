Installer contract

What an installer built on K does in every situation: for each way a request can arrive, each machine it can land on, and each way it can end. K's transaction is code and is fixed. This contract wraps it, and is advisory.

Still settling. Nothing here is K code; K ships the transaction, bootstrapStable, the lock protocol and the receipts this contract relies on. The first implementation is raft-computer-installer; the wording here will follow what that work finds.

The problem

A request comes from one of three places: a person at the shell, the application itself, or a remote authority. It arrives with someone present to answer a question, or unattended. And it lands on a machine in one of five worlds: nothing installed, an installation K manages, one still mid-upgrade, one installed before K existed, or one that cannot start.

Two facts couple these. The application and a remote authority can reach only a machine where the application runs; a machine that cannot start is reachable from the shell alone. And an upgrade can be rolled back, but a repair cannot, so a repair needs consent from someone who can see the result. The same request therefore means different things on different machines, and a request with nobody present must already carry its exact version and its consent.

Most installers answer the common combinations and improvise the rest. The improvised ones are where machines get stuck: a retry that installs over a half-finished upgrade, a remote push that repairs without anyone consenting, a success printed before the new process was ever probed. The contract below gives every combination one answer.

One request

Whatever the entry, the installer receives the same thing: an id, an exact version and recorded consent. A channel name is not a version; the entry resolves it to one and records who approved that one. A request selects nothing else: no code, no commands, no download URLs. The same id sent twice replays the first receipt and touches nothing.

Whether a person is present is decided once, before anything else, and every prompt, retry and printed line keys off it. An explicit CI or *_NON_INTERACTIVE=1 variable wins; otherwise a tty decides. Unattended means nothing may prompt and nothing may be assumed: a request without an exact version and consent is refused before anything changes.

Three entries

Each entry decides who consents and which worlds it can reach. All three launch the same external installer, outside the application's service unit, and the run from there on is identical.

Five worlds

A caller sees three machines: empty, running, or not starting. The installer distinguishes five, because two of them look like one of those three from outside. It reads the world only after settling any unfinished K work, and acts on it as follows.

Every outcome, both ways

Repair

Repair is the one forceful thing the installer does, and it is the installer's, not K's. The rules:

  • Repair is its own request with its own id and explicit consent for this machine. A failed upgrade never escalates to it, and a request that only names a version cannot reach it.
  • It runs recovery first and refuses while a K lock owner is alive.
  • It quarantines K's state directory by one atomic rename and deletes nothing. Application data outside the slots is never touched.
  • It stops an unresponsive service only by an identity it recorded, such as executable path and start time, never by a bare pid.
  • It acquires and verifies the release exactly as an upgrade would, installs, starts, probes, then bootstrapStable, so the next upgrade is a normal transaction.
  • It has no rollback. Its receipt says repaired, never promoted, and names what was quarantined, what was installed and who approved it. If the reinstalled service fails the probe, the receipt is failed and the quarantine is left for an operator.

What a repair must keep so that K's state stays sound is the normative repair boundary. Whether to offer repair at all is a product choice.
