升级是对程序做运维，
执行者应在程序外面。

安装脚本、自更新命令和 Web 作业共同调用一个下载后即用的 K 执行器。应用只暴露停机、启动和健康接口；应用被停掉时，升级仍能继续。

消除什么，保留什么

偶然复杂度本次处理必要能力
成功升级会杀掉负责升级的进程由独立执行器拥有事务停机后仍能完成或恢复
安装入口各做一套交换与回滚只保留一个 K 事务引擎可信字节校验、稳定槽保留
旧客户端没确认收件，升级永远堵住先归档终态回执，再开始新操作保留审计，不谎称已送达
重试再次执行，或把异常说成已回滚在锁内绑定请求与目标；重放记录；异常保留原始状态并发互斥、真实结果与恢复能力

rustup 给出的启发

安装 shell 主要下载并执行 rustup-init；self-update 也会获取执行器。可借鉴的是这个执行边界，不是“临时程序没有版本、状态或兼容性问题”。K 仍然需要持久事务，以及应用数据能否回滚的明确约定。

调研还对照了 Tailscale 的安装与重启分离，并复查了 Datadog 已发布的 installer/experiment 接口。详细事实、来源与设计推论分开记录在 调研文档。

应用需要提供的能力

操作返回前需要成立的事实
quiesce停止接新任务，在途工作可安全暂停；重复调用安全
stop旧实例真正停止，不能只报告“已发送停止请求”
start按指定槽启动；重复调用不产生两个常驻实例
probe版本、PID、实例标识来自同一个活进程；等待其就绪
resume新版本和回滚后的旧版本都能恢复工作

已有的可运行证明

示例服务不导入 K。测试构建独立 runner，在真实进程上做 1→2 升级、错误版本回滚、当前和历史回执重放，并在“停止旧服务、尚未启动新服务”之间杀掉 runner。随后移除分发清单，由另一个 runner 离线恢复，回读服务版本与运行实例。

pnpm test:external 执行本次验收；pnpm check 执行整个仓库检查。源码、测试与设计都在同一个 PR #8。

明确的边界

本次交付 K 框架和独立 Node 24 runner 的打包方式，不发布 Computer 版本，也不替换生产 install.sh。Mac/Windows 真机、原生二进制打包和 Computer 数据/agent 保留，需要应用接入验收；不能用这个示例替代。

临时 runner 仍要在应用的进程管理范围之外启动。单纯 spawn 不保证逃离 systemd cgroup 或 Windows job；断电后还需要外部 supervisor 或操作者再次触发恢复。二进制回滚也不会自动撤销不可逆的数据迁移。
