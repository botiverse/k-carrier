How an upgrade works

How K upgrades a machine nobody operates: one external installer, one journaled transaction, one receipt, and a defined answer for every way it can go wrong.

Who can ask for what

Nothing in this section is specific to K; it is the shape of the problem any external installer has. What may be asked depends on two things: whether the application is running, which decides who can reach the machine at all, and whether the action is reversible, which decides who may approve it. An upgrade can be rolled back. A repair cannot, so it needs explicit consent from someone who can see the result.

self upgrade is a convenience over install.sh: it resolves a channel to a version and asks for consent, then runs the same bootstrap with a pinned installer, launched outside the application's service unit because the installer is about to stop that application. The farther the approver is from the machine, the narrower the action, and in every cell success is claimed only after a live probe, never when the request was accepted.

What each requester must do with each outcome

K gives every operation an exit code and a receipt. What to say, whether to ask, and whether to try again are the entry's job, and the answer differs by whether a person is present. Interactive means a person at the shell who can be asked and can see the result. Non-interactive means a remote request or a script, where nothing may prompt and nothing may be assumed.

What is already on the machine

The second constraint: the same request means something different depending on what is already there. There are five starting worlds. K's transaction covers two, the managed machine and the one still upgrading; the installer decides the rest.

An upgrading machine, one with an unfinished operation in its journal, is finished first, whatever was asked; that recovery is mandatory and is not repair. Only the managed and upgrading worlds have rollback. Fresh and adopted have verification and a probe; broken has consent and a receipt.

K's answer: the pieces

One external installer, launched from every entrypoint, that owns the transaction and outlives the application it replaces. It has a small number of parts.

Bootstrap
Your install.sh, or the self upgrade command inside your application. Downloads and verifies the installer, launches it, relays the exit code. Contains no upgrade logic.
Installer
What you ship, in two halves. The supervisor is a temporary process that acquires and verifies the runner, executes it and, if it dies, runs bounded recovery. The runner is K plus your adapter bundled into one executable; it serves one request and exits. A running runner is a worker.
Adapter
Your trusted code, fixed at build time: where releases come from, whether an upgrade may proceed, how to reach the controller.
Controller
Your program that actually stops, starts and probes the application. The adapter calls it directly or through createCommandHost.
State directory
The lock, the journal, two slots and the receipts. Recovery needs this state, a compatible runner, its runtime and the controller. It does not need release distribution.

The slots are stable and experiment. They are positions on disk, not release channels; a product channel also called "stable" is unrelated. Hands is K's sibling project for the publishing side; K works with it or with any manifest source.

One upgrade, start to finish

  1. bootstrap Asks the supervisor for one operation: an id and a target version. The id is what everything else binds to.
  2. supervisor Downloads the runner, checks its hash and size, writes it to scratch space and runs it with the request on stdin.
  3. worker Takes the installation lock. An unfinished earlier operation is settled first. The same id replays its result; a new id may proceed only after recovery succeeds. controller is asked to fence any effects of an earlier worker.
  4. worker Asks your release source for exactly the target version, verifies the bytes, writes them into the experiment slot. Nothing running has changed yet.
    journal: staged
  5. controller Quiesces, parking in-flight work, then stops the current service and confirms the old process is gone.
    journal: handing-over, with the pre-stop startId
  6. controller Starts the candidate from the experiment slot. worker probes it. The probe must come from one live process and report the expected version, a pid and a startId. If the startId journaled before the stop comes back now, the old process was never replaced and the upgrade rolls back.
    journal: running-experiment, readback
  7. worker Writes promote intent. Before this line, the safe move is always to put the old version back; after it, the safe move is always to finish the promotion.
    journal: promote intent
  8. worker Experiment becomes stable. controller resumes parked work. The receipt is persisted in operation.json and archived before any later operation begins. The worker prints its response and exits 0; the supervisor relays it.

Operation receipts also track stages such as downloading and policy outcomes such as held; those are not journal phases.

When something goes wrong

The candidate is bad

It does not start, it reports the wrong version, or it never passes the probe. The worker stops it, starts stable again, resumes parked work, and records rolled-back. Exit code 1. The stable bytes were never touched. This is the routine failure and the one K is built around.

The worker dies

A crash, a kill, or a budget timeout. The supervisor:

  1. terminates a timed-out worker and waits for its observed exit; a deadline alone does not permit takeover;
  2. starts a recovery worker bound to the same operation id;
  3. that worker takes the lock, checks the operation identity, and asks the controller to fence before replaying lifecycle effects, so actions queued by the earlier worker cannot land later. An already terminal operation simply replays its receipt.

Recovery needs no network and does not guess. It reads the journal and does one of two things. Recovery never starts a new upgrade, even if the original request was one.

Attempts and elapsed time are bounded. If recovery does not settle within them, the supervisor exits 3, leaves the verified runner and a recovery.json in scratch space, and prints where. resumeRunner on that file retries the same recovery offline.

Everything dies

Power loss, reboot, or the whole invocation killed. The state directory survives. The next installer invocation, from install.sh, from self upgrade, or from an operator, settles the unfinished operation before it accepts new work. K does not install a permanent watchdog, so something has to run the installer again: your product's OS startup hook, or a person.

Beyond recovery

Recovery settles K's own work; it cannot help in the broken world, where K refuses rather than guesses. The installer, which runs when the application cannot, may then repair on explicit consent: quarantine K's state directory, reinstall verified bytes from a trusted release, start, probe, and bootstrapStable the result so the next upgrade is a normal transaction. A repair has no rollback and is reported as a repair. The design states the obligations; the integration guide shows how to build one.

Every run prints one JSON response on stdout and returns an exit code. Inspect both.

Two things surprise people. A recover that successfully restored stable after a bad candidate exits 1, because the recorded outcome is a rolled-back upgrade. That is the honest answer. And status reads the last receipt, not the live service; it can say genesis on a machine that is running fine.
